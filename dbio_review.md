# Обзор модуля отладочного ввода-вывода (dbio.c / dbio.h)

Дата обзора: 2026-08-15
Проект: PIC18F46J50_TEST.X

---

## 1. Назначение и общая логика

Модуль реализует буферизованный обмен по UART1: два кольцевых буфера по 200 байт
(`RXbuf` / `TXbuf`, `dbio.c:5-12`), два обработчика прерываний, регистрируемых
в общем низкоприоритетном диспетчере (`system.c:64`), и две функции прикладного
уровня — `dbio_getstring` / `dbio_putstring`.

- Приём: `RXbyte_cbk` (`dbio.c:31`) по прерыванию `RC1IF` вычитывает байт из
  `RCREG` и кладёт его в `RXringbuf`.
- Передача: `dbio_putstring` кладёт строку в `TXringbuf` и, если передатчик
  свободен, отправляет первый байт и включает прерывание `TX1IE`; дальше буфер
  дренирует `TXbyte_cbk` (`dbio.c:16`), выключая прерывание по опустошению.
- Сборка строки на приёме сделана по таймауту межсимвольной паузы: пока объём
  данных в буфере растёт, функция возвращает `0`; строка отдаётся, когда объём
  не изменился в течение `timeout` мс (`dbio.c:70-95`).
- Аппаратная привязка вынесена в макросы `dbio.h:6-12` поверх `U1_*` из
  `system.h:18-24` — перенос модуля на UART2 потребует правки только заголовка.

Что сделано правильно и стоит сохранить при доработке:

- Все обращения к кольцевым буферам из основного кода обёрнуты в
  `InterruptDis()` / `InterruptEn()` — требование `ringbuf` о внешней
  синхронизации соблюдено.
- Оба callback'а проверяют пару «разрешение + флаг» (`TX1IE && TX1IF`,
  `RC1IE && RC1IF`). Это обязательно, поскольку диспетчер `system.c:64`
  вызывает по прерыванию **все** зарегистрированные обработчики подряд.
- Аппаратная ошибка переполнения приёмника (`OERR`) хотя бы сбрасывается,
  без чего приём «залипает» навсегда.

## 2. Ошибки

### 2.1. Потеря байта и завышенный возврат при длинной строке

`dbio.c:75-80`:

```c
RingBuf_DataRead(str, Nmax, &RXringbuf);   // вычитали Nmax байт из кольца
...
str[(Nmax-1)] = '\0';                      // последний из них затёрли
return (int)Nmax;                          // а сообщили Nmax символов
```

Из кольца извлекается `Nmax` байт, но `Nmax`-й затирается терминатором —
байт данных теряется безвозвратно (в кольце его уже нет). Дополнительно
возвращается `Nmax`, хотя валидных символов `Nmax-1`.

**Рекомендация:** читать `Nmax-1` байт и возвращать `Nmax-1`.

### 2.2. Запись за границу буфера вызывающей стороны

`dbio.c:88-92`:

```c
buf_len = (buf_len > Nmax) ? Nmax : buf_len;
...
str[buf_len] = '\0';     // при buf_len == Nmax это str[Nmax]
```

Клипование должно быть до `Nmax-1`: место под терминатор в `Nmax` не заложено.

**Проявление в проекте:** при одном вызывающем с постоянным `Nmax` состояние
`buf_len_prev` в эту ветку с `buf_len >= Nmax` попасть не даёт. Но `buf_len_prev`
и `timetmp` объявлены `static` и общие для всех вызовов: достаточно вызвать
функцию с большим `Nmax`, а следующий раз — с меньшим при том же объёме данных
в кольце (например, 100, затем 50), и запись за границу становится реальной.
В `main.c:71` от последствий спасает только запас `strrx[100]` против `Nmax=50`.

**Рекомендация:** клиповать до `Nmax-1`; состояние таймаута либо вынести в
структуру-контекст, либо явно задокументировать как «модуль рассчитан на
единственного вызывающего с постоянным `Nmax`».

### 2.3. Отправка неинициализированного байта при пустой строке

`dbio.c:120-130`. Если `str_len == 0`, в буфер ничего не кладётся, но код всё
равно входит в ветку `CheckTxPermission()`:

```c
RingBuf_DataRead(&byte, 1, &TXringbuf);   // при пустом кольце вернёт RINGBUF_EMPTY
SendByte(byte);                            // ...не изменив byte
```

`RingBuf_DataRead` на пустом буфере возвращает `RINGBUF_EMPTY` через
`RingBuf_DataWatch` (`ringbuf.c:136`), **не трогая** выходную переменную.
В линию уходит содержимое неинициализированной `byte`, попутно включается
прерывание передачи. Статус `RingBuf_DataRead` не проверяется нигде в модуле.

**Рекомендация:** ранний выход при `str_len == 0` и проверка кода возврата.

### 2.4. После сброса OERR в приёмное кольцо попадает мусор

`dbio.c:36-42`:

```c
if(RCSTAbits.OERR) { RCSTA1bits.CREN = 0; RCSTA1bits.CREN = 1; overrun_errors++; }
byte = GetByte();          // выполняется и в случае OERR
RingBuf_DataPut(&byte, 1, &RXringbuf);
```

Сброс `CREN` очищает приёмный FIFO, поэтому последующее чтение `RCREG` даёт не
принятые данные, а пустое/устаревшее значение — и оно попадает в `RXringbuf`
как валидный символ.

Также не обрабатывается `FERR` (framing error): при рассинхроне скорости
искажённые байты уходят в буфер наравне с корректными.

**Рекомендация:** сначала вычитать `RCREG` (FIFO двухуровневый — два чтения),
затем тоггл `CREN`, и в этой итерации байт в кольцо не класть; аналогично
отбрасывать байт при `FERR`. Заодно привести к единому виду имена `RCSTAbits`
и `RCSTA1bits` (это один и тот же регистр).

### 2.5. Гонка за `TXREG` между `dbio_putstring` и обработчиком передачи

`dbio.c:124-130`. Проверка `CheckTxPermission()` (это `TX1IF`), чтение байта из
кольца и `SendByte()` не образуют единой критической секции — между ними
прерывания включены:

```c
if(CheckTxPermission())
{
  InterruptDis();
  RingBuf_DataRead(&byte, 1, &TXringbuf);
  InterruptEn();                 // <-- здесь может сработать TXbyte_cbk
  SendByte(byte);                // и перезаписать уже занятый TXREG
}
```

Если передача уже идёт (`TX1IE == 1`) и `TX1IF` установлен, сразу после
`InterruptEn()` срабатывает `TXbyte_cbk`, тоже вызывает `SendByte`, а следом
основной код перезаписывает `TXREG` до того, как байт ушёл в сдвиговый регистр.
Результат — потерянный либо переставленный байт. Окно узкое (несколько
инструкций), но воспроизводимое при активной передаче.

**Рекомендация:** заключить блок «проверка -> чтение -> `SendByte` -> `TxIntEn`»
в одну критическую секцию. Более надёжный вариант — вообще не отправлять байт
из `dbio_putstring`: класть данные в буфер и вызывать `TxIntEn()`, отдав всю
отправку обработчику.

### 2.6. Проверка свободного места использует `Nmax` вместо реальной длины строки

`dbio.c:118`:

```c
if((buf_len + Nmax + 1) > BUFLENGTH) return -1;
```

`str_len` вычисляется только на следующей строке (`dbio.c:120`), а решение об
отказе принимается по `Nmax` — то есть по размеру буфера вызывающего, а не по
объёму передаваемых данных.

**Проявление в проекте:** `main.c:61` вызывает `dbio_putstring(strtx, 100)`.
Как только в `TXringbuf` окажется больше 99 байт, короткая строка будет молча
отброшена, хотя места достаточно.

**Рекомендация:** считать `str_len` до проверки и сравнивать с `BUFLENGTH-1`
(полезная ёмкость кольца на единицу меньше — `head == tail` трактуется как
«пусто»).

### 2.7. Переполнение приёмного кольца никак не фиксируется

`dbio.c:42`. `RingBuf_DataPut` при заполненном буфере не отбрасывает новые
данные, а сдвигает `tail` (`ringbuf.c:90`), то есть **молча затирает самые
старые непрочитанные байты**. Возврат функции игнорируется, счётчик ведётся
только для аппаратного `OERR` (`overrun_errors`), который в этом сценарии не
взводится.

**Проявление в проекте:** в основном цикле `main.c:84` стоит `delay_ms(500)`,
а 200 байт на 230400 бод принимаются за ~8.7 мс. При потоке данных длиннее
буфера часть строки теряется без единого признака.

**Рекомендация:** проверять код возврата `RingBuf_DataPut` и вести отдельный
счётчик программных переполнений приёма.

### 2.8. Не отсекается `Nmax == 0`

`dbio.c:62` проверяет только верхнюю границу (`Nmax > BUFLENGTH`). При
`Nmax == 0` ветка таймаута выполнит `str[0] = '\0'` в буфер нулевого размера.

## 3. Замечания по надёжности и стилю

### 3.1. Критические секции не вкладываются

`InterruptEn()` (`system.h:27`) безусловно ставит `GIE = 1`. Если
`dbio_putstring` будет вызвана из уже закрытой критической секции или из
ms-callback (`system.c:55`), прерывания включатся преждевременно.

**Рекомендация:** сохранять и восстанавливать `INTCONbits.GIE` (или
использовать пару макросов вида `CRITICAL_ENTER/CRITICAL_EXIT` с локальной
переменной состояния).

### 3.2. Избыточные `static` у локальных переменных

`buf_len` в `dbio.c:59` и `dbio.c:112` перезаписывается при каждом вызове и
состояния между вызовами не хранит — это лишний расход статического ОЗУ и
ложный намёк на разделяемое состояние. Реально разделяемые здесь только
`timetmp` и `buf_len_prev` (см. 2.2).

### 3.3. Лишняя глобальная видимость

`RXringbuf`, `TXringbuf`, `RXbuf`, `TXbuf`, `overrun_errors`, `TXbyte_cbk`,
`RXbyte_cbk`, `dbio_strnlen` не объявлены `static`, хотя за пределами модуля не
используются. Кроме засорения пространства имён, `overrun_errors` изменяется в
обработчике прерывания и должен быть `volatile`, если его читать из основного
кода, — но геттера для него в `dbio.h` нет, и сейчас счётчик недоступен.

### 3.4. Не проверяются коды возврата регистрации обработчиков

`dbio.c:50-51`: `sys_regiter_IRQ_clbk` возвращает ненулевой код при исчерпании
таблицы (`system.c:23`). Сейчас при переполнении таблицы обработчик молча не
зарегистрируется, и модуль перестанет работать без какой-либо диагностики.

### 3.5. Избыточный вызов `RxIntEn()`

`dbio.c:53` дублирует `PIE1bits.RC1IE = 1`, уже выполненное внутри
`UART1_Init()` (`system.c:165`).

### 3.6. Отсутствие `const` в сигнатуре передачи

`dbio_putstring(char* str, ...)` не помечает вход как `const char*`, из-за чего
в `main.c:67` строковые литералы передаются в неконстантный параметр.

### 3.7. Недокументированные коды возврата

`dbio_getstring` возвращает `-1` (некорректный параметр), `-2` (данных пока
нет), `0` (приём строки продолжается) и положительную длину. Смысл `-2` легко
принять за ошибку; коды стоит вынести в enum и описать в заголовке.

### 3.8. Мелочи

- `#include <string.h>` (`dbio.c:3`) не используется.
- Избыточные касты: `(uint8_t*)&byte` (`dbio.c:24`, `dbio.c:42`),
  `(uint16_t*)&buf_len` (`dbio.c:65`) — типы и так совпадают.
- Закомментированный `RingBuf_Clear` (`dbio.c:77`) — либо удалить, либо
  пояснить, почему остаток данных сознательно сохраняется.
- Комментарий include-guard в `dbio.h:18` говорит `DEBUGIO_UART1_H`, тогда как
  сам guard — `DBIO_H`.
- В прототипе (`dbio.h:15`) параметр назван `ch`, в реализации — `str`.

## 4. Итог

Архитектура модуля корректна: разделение «ISR <-> основной код» через кольцевые
буферы сделано правильно, критические секции расставлены, аппаратная привязка
изолирована макросами. Основные проблемы — в краевых случаях: границы строки,
обработка ошибок приёмника и незащищённый доступ к `TXREG`.
