# Обзор модуля кольцевого буфера (ringbuf.c / ringbuf.h)

Дата обзора: 2026-08-14
Проект: PIC18F46J50_common_project.X

---

## 1. Назначение и общая логика

Модуль реализует классический кольцевой буфер с поддержкой произвольного размера
ячейки (`cell_size`), с оборачиванием (wrap-around) при записи/чтении и с политикой
«перезаписи старых данных» при переполнении.

- `head` — указатель записи, `tail` — указатель чтения (`ringbuf.h:17-19`).
- Пустой буфер определяется как `head == tail`. Из-за этого соглашения буфер
  жертвует одной ячейкой — реально влезает `size - 1` элементов, а не `size`.
  В `dbio.c:118` это учтено (`(buf_len + Nmax + 1) > BUFLENGTH`), поэтому для
  UART-очередей проблемы не возникает.
- При нехватке места `RingBuf_DataPut` не отбрасывает новые данные, а сдвигает
  `tail` вперёд (`ringbuf.c:90`: `if((rb->size - avaldat) <= len_tmp) rb->tail = rb->head + 1;`),
  то есть отбрасывает самые старые непрочитанные байты. Поведение
  «перезаписать старое» реализовано корректно для основных сценариев.
- `RingBuf_DataRead` / `RingBuf_DataWatch` корректно обрабатывают перенос через
  конец массива (паттерн `space` / `s_addr`), включая арифметику по `cell_size`.

## 2. Найденные замечания

### 2.1. Скрытый баг: запись ровно `rb->size` ячеек за один вызов теряет 1 ячейку

`ringbuf.c:59` пропускает случай `len == rb->size`:

```c
if (len > rb->size)
    return RINGBUF_OVERFLOW;
```

Из-за соглашения «одна ячейка в жертву» после такой записи `tail = head + 1`
обрезает ровно ту ячейку, что была записана первой — она физически лежит в
буфере, но становится недостижима для чтения.

**Проявление в проекте:** сейчас отсутствует, т.к. единственные вызовы
`RingBuf_DataPut` — по 1 байту (`dbio.c:42`) либо ограничены запасом в 1 байт
(`dbio.c:118`, `dbio.c:122`). При прямом использовании модуля в другом месте
баг может выстрелить.

**Рекомендация:** либо явно отклонять `len >= rb->size`, либо пересмотреть
формулу сдвига `tail`.

### 2.2. Нет проверки `data == NULL` в `RingBuf_DataPut`

В отличие от `RingBuf_DataWatch` (`ringbuf.c:132`), функция `RingBuf_DataPut`
сразу кастует и разыменовывает входной указатель (`ringbuf.c:61`). API
несимметричен по строгости проверок.

### 2.3. Отсутствие атомарности внутри модуля

Функции не отключают прерывания самостоятельно — корректность при конкурентном
доступе (ISR пишет, main читает) целиком лежит на вызывающем коде.

В `dbio.c` требование соблюдается (`InterruptDis()` / `InterruptEn()` вокруг
каждого вызова), но нигде в `ringbuf.h` это не задокументировано — при следующем
использовании модуля об этом легко забыть.

**Рекомендация:** добавить явное предупреждение в заголовок модуля.

### 2.4. Смешение типов `size_t` и `uint16_t`

Поля структуры объявлены как `size_t` (`ringbuf.h:18-21`), но публичный API
оперирует `uint16_t` (`RingBuf_Available`, параметр `len` в `Put`/`Read`/`Watch`).

На PIC18 (XC8, `size_t` = 16 бит) это безобидно. Но при переносе модуля на
платформу с более широким `size_t` значения `head - tail` будут молча усекаться
при записи через `uint16_t*`.

### 2.5. Мелкие стилистические нюансы

- `#pragma once` вместе с классическими include-guard'ами (`ringbuf.h:1-4`) —
  избыточно, хотя и безвредно.
- Доккомментарии `@param len Length ... [bytes]` не совсем точны: длина
  считается в ячейках (`cell_size`), а не всегда в байтах.
- `RingBuf_DataWatch` возвращает `RINGBUF_EMPTY` даже при запросе `len == 0`
  на пустом буфере — тривиальный, но не вполне логичный краевой случай.

## 3. Итог

Модуль работоспособен и корректно используется в проекте: в `dbio.c` вызовы
всегда защищены запасом в одну ячейку и обёрнуты в `InterruptDis()/InterruptEn()`.

| 2.2 | Нет проверки `data == NULL` в `DataPut` | Низкий |

| 2.5 | Стилистика и точность документации | Низкий |
