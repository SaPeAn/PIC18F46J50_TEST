# Часть 1. Как устроен USB

## 1.1. Главный принцип: хост командует, устройство молчит

Это единственное, что нужно усвоить до всего остального. В USB **нет**
симметричного обмена. Шиной полностью управляет хост (ПК). Устройство физически
не может начать передачу — оно только отвечает на запросы. Даже когда клавиатура
«отправляет» нажатие, на самом деле происходит вот что: хост каждые N
миллисекунд спрашивает «есть что?», а устройство либо отдаёт готовый пакет, либо
отвечает NAK («пока нет»).

Отсюда следует важное для прошивки: вся логика устройства — реактивная. Вы не
пишете «отправить отчёт», вы пишете «положить отчёт в буфер и передать его во
владение железу, чтобы оно отдало данные, когда хост в следующий раз спросит».

## 1.2. Физика

Две сигнальные линии, `D+` и `D-`, работают дифференциально. Скорость хост
определяет по тому, на какую линию устройство повесило подтягивающий резистор
1,5 кОм к 3,3 В:

| Подтяжка | Скорость | Полное имя |
|---|---|---|
| на `D+` | 12 Мбит/с | Full Speed |
| на `D-` | 1,5 Мбит/с | Low Speed |
| на `D+` + чирп при сбросе | 480 Мбит/с | High Speed (USB 2.0) |

До подключения подтяжки обе линии притянуты хостом вниз — состояние **SE0**
(Single-Ended Zero, обе линии в нуле). Как только устройство включает подтяжку,
хост видит изменение и понимает: кто-то подключился. Это и есть «attach».

Затяжной SE0 (>2,5 мкс) со стороны хоста — это **USB Reset**, команда «забудь
всё, начни с нуля».

## 1.3. Логическая иерархия

```
Устройство (Device)
 └── Конфигурация (Configuration)      ← обычно одна; хост выбирает её командой
      └── Интерфейс (Interface)         ← одна функция: клавиатура / микрофон / диск
           └── Endpoint (конечная точка) ← однонаправленный «канал» данных
```

**Endpoint** — ключевое понятие. Это буфер в устройстве с номером (0…15) и
направлением. Направление всегда называется **с точки зрения хоста**:

- **IN** — данные идут в хост (устройство → ПК)
- **OUT** — данные идут из хоста (ПК → устройство)

Адрес endpoint кодируется байтом: младшие 4 бита — номер, старший бит —
направление. `0x81` = EP1 IN, `0x01` = EP1 OUT.

**Endpoint 0 — особенный.** Он обязателен, двунаправленный (EP0 IN + EP0 OUT), и
существует ещё до того, как хост что-либо узнал об устройстве. Через него идёт
всё управление.

## 1.4. Транзакция

Минимальная неделимая единица обмена. Три фазы, каждая — пакет со своим PID
(Packet ID):

```
       ХОСТ                      УСТРОЙСТВО
        |                            |
   (1)  |---- TOKEN ---------------->|   «EP1, направление IN»  (PID: IN/OUT/SETUP)
        |                            |
   (2)  |<--- DATA ------------------|   полезные данные        (PID: DATA0/DATA1)
        |                            |
   (3)  |---- HANDSHAKE ------------>|   подтверждение          (PID: ACK/NAK/STALL)
```

- **TOKEN** — хост всегда шлёт первым: адрес устройства + номер endpoint + тип.
- **DATA** — идёт в ту сторону, которую задал токен. Для IN — от устройства, для
  OUT/SETUP — от хоста.
- **HANDSHAKE**: `ACK` — принято; `NAK` — «занят, спроси позже» (не ошибка!);
  `STALL` — «не поддерживаю / ошибка, нужен сброс endpoint».

### DATA0/DATA1 — защита от потери подтверждения

Тонкий, но обязательный механизм. Представьте: устройство отправило данные, хост
принял и послал ACK, но ACK потерялся в кабеле. Устройство считает, что данные не
дошли, и шлёт их снова — хост получит дубликат.

Решение: у каждой стороны есть бит-переключатель. Пакеты помечаются попеременно
`DATA0`, `DATA1`, `DATA0`… Приёмник, увидев пакет с тем же PID, что и предыдущий,
понимает — это повтор, данные отбрасывает, но ACK шлёт снова. Этот бит называется
**DTS** (Data Toggle Synchronization).

## 1.5. Четыре типа передач

| Тип | Гарантия | Применение |
|---|---|---|
| **Control** | доставка гарантирована, полосы нет | управление, только EP0 |
| **Interrupt** | хост опрашивает не реже заданного периода | клавиатуры, мыши |
| **Bulk** | доставка гарантирована, время — нет | флешки, принтеры |
| **Isochronous** | время гарантировано, доставка — нет | звук, видео |

Наш проект использует ровно два первых: control на EP0 и interrupt на EP1 IN.

Время на шине нарезано на **кадры** по 1 мс. Начало каждого хост отмечает пакетом
**SOF** (Start Of Frame). Для устройства SOF — бесплатный тик на 1 мс, очень
удобный.

## 1.6. Control-передача: три стадии

```
+-------------+   +------------------+   +-------------+
|   SETUP     |-->|   DATA (опц.)    |-->|   STATUS    |
|  8 байт     |   | несколько пакетов|   | пустой пакет|
+-------------+   +------------------+   +-------------+
```

**SETUP** — всегда ровно 8 байт, всегда DATA0:

| Смещение | Поле | Смысл |
|---|---|---|
| 0 | `bmRequestType` | бит 7 — направление данных, биты 6:5 — класс запроса (0 = стандартный, 1 = class), биты 4:0 — получатель |
| 1 | `bRequest` | код запроса |
| 2–3 | `wValue` | параметр |
| 4–5 | `wIndex` | параметр |
| 6–7 | `wLength` | сколько байт данных ожидается в стадии DATA |

**DATA** — если `wLength > 0`. Данные режутся на пакеты по `bMaxPacketSize0`
байт.

**STATUS** — пакет нулевой длины **в обратную сторону** от DATA. Это
подтверждение «команда выполнена». Если данных не было, статус всегда IN
(от устройства).

Правило коротких пакетов: передача данных заканчивается, когда пришёл пакет
**короче** максимального размера. Если данные точно кратны `bMaxPacketSize`, а
запрошено было больше — нужно дослать пустой пакет (**ZLP**, zero-length packet),
иначе хост будет ждать продолжения.

## 1.7. Энумерация — что происходит при подключении

```
1.  Устройство включает подтяжку          -> хост видит attach
2.  Хост: USB Reset                       -> устройство: адрес 0, только EP0
3.  Хост: GET_DESCRIPTOR(Device, 8 байт)  -> узнаёт bMaxPacketSize0
4.  Хост: USB Reset (ещё раз)
5.  Хост: SET_ADDRESS(n)                  -> устройство переезжает на адрес n
6.  Хост: GET_DESCRIPTOR(Device, 18 байт) -> VID/PID/классы
7.  Хост: GET_DESCRIPTOR(Config)          -> сначала 9 байт, потом целиком
8.  Хост: GET_DESCRIPTOR(String)          -> названия для диспетчера устройств
9.  Хост: SET_CONFIGURATION(1)            -> устройство включает свои endpoint
10. (для HID) GET_DESCRIPTOR(Report)      -> как трактовать байты отчётов
11. Хост: SET_IDLE, SET_PROTOCOL          -> настройка HID
12. Поехали: хост опрашивает EP1 IN каждые bInterval мс
```

Состояния устройства по ходу: **Detached → Default (адрес 0) → Addressed →
Configured**. Работать можно только в Configured.

**Критическая тонкость шага 5:** новый адрес нельзя применять сразу при получении
SETUP — статусную стадию этой же передачи хост ещё адресует по **старому** адресу.
Адрес меняется только после её завершения. Это классическое место, где самописные
стеки ломаются.

## 1.8. HID и клавиатура

HID (Human Interface Device) — класс, где устройство само описывает формат своих
данных через **Report Descriptor**: байт-код вида «Usage Page = Keyboard, 8 бит
модификаторов, 6 байт кодов клавиш».

Для клавиатур и мышей есть упрощение — **Boot Protocol**: фиксированный формат,
который понимает даже BIOS, не умеющий парсить report descriptor. Boot-отчёт
клавиатуры — 8 байт:

```
байт 0 : модификаторы   (бит0=LCtrl, 1=LShift, 2=LAlt, 3=LGui, 4..7 — правые)
байт 1 : зарезервирован (всегда 0)
байт 2 : usage ID клавиши №1   <- до шести одновременно нажатых
байт 3 : usage ID клавиши №2
...
байт 7 : usage ID клавиши №6
```

**Usage ID — это не ASCII.** `0x04` = «клавиша A», `0x1E` = «клавиша 1». Что при
этом появится на экране, решает раскладка в ОС. Чтобы получить `A`, надо послать
usage `0x04` **и** модификатор LShift.

И главное: отчёт описывает **состояние**, а не событие. «Нажато A» — это отчёт
`[0x00,0,0x04,0,0,0,0,0]`, а «отпущено» — отчёт `[0x00,0,0x00,0,0,0,0,0]`. Без
второго отчёта клавиша залипнет и пойдёт автоповтор. Каждый символ = **два**
отчёта.

Обратный канал — светодиоды (Num/Caps/Scroll Lock). Хост шлёт их запросом
`SET_REPORT` через EP0.

# Часть 2. Как это сделано в проекте

## 2.1. Железо: SIE и Buffer Descriptor Table

В PIC18F46J50 весь низкий уровень — NRZI-кодирование, bit stuffing, CRC, PID,
ACK/NAK, распознавание токенов — делает аппаратный блок **SIE** (Serial Interface
Engine). Прошивка не видит ни одного бита на проводе.

Общение с SIE идёт через **BDT** — таблицу дескрипторов буферов в двухпортовой
памяти. По одной записи на каждое направление каждого endpoint, 4 байта
(`USB.c:86`):

```c
typedef struct {
  uint8_t STAT;   // статус/управление
  uint8_t CNT;    // счётчик байт
  uint8_t ADRL;   // адрес буфера, младший байт
  uint8_t ADRH;   // адрес буфера, старший байт
} BD_t;
```

### UOWN — кто владелец

Старший бит `STAT` решает всё:

- **`UOWN = 1`** — буфер принадлежит SIE. Прошивке **нельзя** его трогать.
  Железо ждёт транзакцию.
- **`UOWN = 0`** — SIE закончил и вернул буфер прошивке. Теперь можно читать
  данные и смотреть, что произошло.

При этом байт `STAT` меняет смысл в зависимости от владельца (`USB.c:11-21`):

```c
// когда пишем мы (UOWN=1) — это флаги управления
#define _UOWN   0x80   // отдать SIE
#define _DTS    0x40   // послать как DATA1 (0 = DATA0)
#define _DTSEN  0x08   // включить проверку toggle
#define _BSTALL 0x04   // ответить STALL

// когда прочитал SIE (UOWN=0) — биты 5:2 стали PID принятого пакета
#define BD_PID(stat) (((stat) >> 2) & 0x0F)
#define PID_SETUP    0x0D
```

Это самая частая ловушка при работе с USB на PIC: один и тот же регистр читается
по-разному в зависимости от `UOWN`.

### Карта памяти

BDT обязан лежать по фиксированному адресу 0x400. Дальше — буферы, разложенные
вручную (`USB.c:94-97`):

```
0x0400 +--------------------+
       | BDT[0] EP0 OUT     |  4 байта
0x0404 | BDT[1] EP0 IN      |
0x0408 | BDT[2] EP1 OUT     |  <- объявлен, но не используется:
0x040C | BDT[3] EP1 IN      |     в UEP1 нет EPOUTEN
0x0410 +--------------------+
       | ep0_out_buf[8]     |  сюда SIE кладёт SETUP и OUT-данные
0x0418 | ep0_in_buf[8]      |  отсюда SIE берёт ответы на EP0
0x0420 | ep1_in_buf[8]      |  8-байтовый boot-отчёт клавиатуры
0x0428 +--------------------+
       ...cstackBANK4h        <- линковщик поставил стек ровно следом,
                                 пересечения нет (проверено по .map)
```

## 2.2. Дескрипторы — паспорт устройства

Это статические массивы в ROM, которые просто отдаются по запросу.

**Device** (`USB.c:109`) — `bMaxPacketSize0 = 8`, VID/PID, `bDeviceClass = 0x00`
(класс определён на уровне интерфейса, а не устройства).

**Configuration** (`USB.c:131`) — один непрерывный блок из четырёх дескрипторов,
отдаётся целиком:

```
байты  0.. 8  Configuration : 1 интерфейс, питание от шины, 100 мА
байты  9..17  Interface     : класс 0x03 (HID), подкласс 0x01 (Boot),
                              протокол 0x01 (Keyboard)
байты 18..26  HID           : <- сюда указывает HID_DESC_OFFSET = 18
байты 27..33  Endpoint      : 0x81 (EP1 IN), Interrupt, 8 байт, bInterval = 10 мс
```

`CFG_TOTAL_LEN = 34` — сумма 9+9+9+7, и это же значение записано в поле
`wTotalLength`. Проверено, сходится.

**Report** (`USB.c:172`) — 63 байта boot-раскладки: 8 бит модификаторов, 1 байт
padding, 5 бит светодиодов + 3 бита выравнивания, 6 байт кодов клавиш. Пересчитано
побайтово — ровно 63, как и объявлено в `REPORT_DESC_LEN`.

**Таблица трансляции** (`USB.c:222`) — `ascii2usage[128]`. Компактный трюк:
старший бит хранит признак Shift.

```c
/* 0x40 */ 0x9F, 0x84, 0x85, ...   // @ A B ...
```

Символ `A` даёт `0x84` = `0x04 | 0x80` = usage «клавиша A» + флаг Shift.
Разбирается в `USB.c:817`:

```c
return USB_kbd_putkey(code & 0x7F,
                      (code & KBD_SHIFT) ? USB_KBD_MOD_LSHIFT : 0);
```

## 2.3. Инициализация — `USB_init()`

`USB.c:726`

```c
UCFG = 0x14;    // UPUEN=1: включить внутреннюю подтяжку D+
                // FSEN=1:  Full Speed
                // UTRDIS=0: внутренний трансивер
                // PPB=00:  без ping-pong буферизации
```

Отсутствие ping-pong заметно упрощает код: у каждого endpoint ровно один буфер,
не надо следить за чётностью.

```c
UCONbits.USBEN = 1;   // вот это и есть «подключение» — подтяжка включается здесь
```

Дальше — аккуратная деталь, которую часто делают неправильно (`USB.c:751`):

```c
uint32_t t0 = get_ms();
while(UCONbits.SE0 && ((get_ms() - t0) < 100));
```

Ждём выхода из SE0, но **с таймаутом**. Если кабель не воткнут, SE0 будет
держаться вечно, и безусловный `while` подвесил бы всю прошивку. Здесь через
100 мс просто идём дальше — а когда кабель воткнут, всё подхватится по прерыванию
URSTIF.

Разрешаются прерывания: `URSTIE` (сброс), `TRNIE` (транзакция завершена),
`IDLEIE` (шина замолчала), `STALLIE`, `UERRIE`, `SOFIE`. Приоритет низкий —
`IPR2bits.USBIP = 0`, в одной группе с UART и АЦП; наверху только миллисекундный
таймер.

## 2.4. Диспетчер прерываний — `USB_isr()`

`USB.c:645`. Вызывается из `system.c:56` уже после проверки `USBIE && USBIF`.
Порядок обработки внутри неслучаен.

**Выход из suspend — первым делом:**

```c
if(UIRbits.ACTVIF && UIEbits.ACTVIE)
{
  UCONbits.SUSPND = 0;
  while(UIRbits.ACTVIF) UIRbits.ACTVIF = 0;  // сбрасывается не с первого раза
  UIEbits.ACTVIE = 0;
}
if(UCONbits.SUSPND) return;
```

Цикл `while` — не паранойя, а документированное поведение: пока модуль
просыпается, флаг переустанавливается.

**Сброс шины:** `usb_reset()` (`USB.c:613`) — обнуляет адрес, гасит EP1, чистит
очередь клавиш, ставит `ST_DEFAULT`. Именно сюда попадает устройство, когда его
втыкают в порт.

**SOF — раз в 1 мс:**

```c
if(UIRbits.SOFIF) { UIRbits.SOFIF = 0; kbd_service(); }
```

Бесплатный тик, на котором подкладывается следующий отчёт.

**Завершённые транзакции:**

```c
while(UIRbits.TRNIF)
{
  uint8_t stat = USTAT;
  UIRbits.TRNIF = 0;          // сброс продвигает FIFO на 4 записи

  uint8_t ep  = (stat >> 3) & 0x0F;
  uint8_t dir = (stat >> 2) & 0x01;   // 1 = IN
  ...
}
```

`USTAT` — это **FIFO глубиной 4**, а не регистр. Значение надо прочитать **до**
сброса `TRNIF`, потому что сброс продвигает очередь. Цикл `while` вместо `if`
нужен, чтобы разгрести все накопившиеся события за один вход в прерывание.
Здесь это сделано правильно.

## 2.5. Машина состояний control-передачи

Сердце модуля. Состояние в `ctrl_stage` (`USB.c:252`):

```
CTRL_IDLE --SETUP c данными IN--> CTRL_IN_DATA --всё послано--> CTRL_STATUS_OUT
    ^                                                                  |
    |                                                   OUT от хоста   |
    +------------------------------------------------------------------+
    |
    +--SETUP без данных--> CTRL_STATUS_IN --пустой IN отправлен--> CTRL_IDLE
    |
    +--SET_REPORT--> CTRL_OUT_DATA --приняли байт светодиодов--> CTRL_STATUS_IN
```

### Приём SETUP — `ep0_setup()`

`USB.c:356`

```c
BDT[BD_EP0_OUT].STAT = 0;
BDT[BD_EP0_IN].STAT  = 0;    // отменяем всё, что было в полёте
ctrl_dts = 1;                // первый DATA-пакет после SETUP — всегда DATA1
UCONbits.PKTDIS = 0;         // SIE заморозил шину — размораживаем
```

`PKTDIS` — ещё одна железная особенность: получив SETUP, SIE **останавливает**
обработку пакетов, чтобы прошивка успела разобраться, и ждёт явного разрешения
продолжить.

Дальше — разбор по `REQ_TYPE(bmRequestType)`: `0x00` — стандартные запросы,
`0x20` — классовые (HID). Всё, что не распознано, падает в `ctrl_stall()`
(`USB.c:342`) — это корректное поведение, хост поймёт «не поддерживается».

### SET_ADDRESS — та самая тонкость

`USB.c:404`

```c
case REQ_SET_ADDRESS:
  pending_addr = wValueL;   // ЗАПОМИНАЕМ, но не применяем
  ctrl_ack();
  return;
```

И только после завершения статусной стадии, в `USB.c:552`:

```c
if(ctrl_stage == CTRL_STATUS_IN)
{
  if(pending_addr) { UADDR = pending_addr; usb_state = ST_ADDRESSED; pending_addr = 0; }
  ctrl_stage = CTRL_IDLE;
}
```

Сделано ровно как требует спецификация.

### Нарезка длинных ответов — `ep0_send_chunk()`

`USB.c:288`. Дескриптор конфигурации (34 байта) не влезает в 8-байтовый EP0,
поэтому уходит пятью пакетами:

```c
uint8_t n = (ctrl_len > EP0_SIZE) ? EP0_SIZE : (uint8_t)ctrl_len;
for(uint8_t i = 0; i < n; i++)
  ep0_in_buf[i] = ctrl_in_rom ? ctrl_rom[ctrl_pos + i] : ctrl_ram[ctrl_pos + i];
ctrl_pos += n;  ctrl_len -= n;

BDT[BD_EP0_IN].CNT  = n;
BDT[BD_EP0_IN].STAT = ctrl_dts ? (_UOWN | _DTS | _DTSEN) : (_UOWN | _DTSEN);
ctrl_dts ^= 1;                        // переключение toggle
```

Обратите внимание: `_UOWN` выставляется **последним** действием, уже после того
как заполнены `CNT` и адрес. Иначе SIE могла бы схватить буфер раньше, чем он
готов.

Каждое завершение IN-транзакции возвращает управление в `ep0_in_done()`
(`USB.c:528`), которое досылает следующий кусок, пока `ctrl_len` не обнулится.

### ZLP — обработка граничного случая

`USB.c:314`

```c
ctrl_zlp = (len < wLength) && (len != 0) && ((len % EP0_SIZE) == 0);
```

Если отдаём ровно 16 байт, а хост просил 64 — 16 кратно 8, короткого пакета не
будет, хост зависнет в ожидании. Поэтому досылается пустой пакет. Условие
покрывает все три требования спецификации сразу.

### Светодиоды — обратный путь

Единственный случай, когда данные идут от хоста. `HID_SET_REPORT` (`USB.c:479`)
переводит машину в `CTRL_OUT_DATA`, а `USB.c:519` забирает байт:

```c
if(BDT[BD_EP0_OUT].CNT >= 1) kbd_leds = ep0_out_buf[0];
ctrl_ack();
```

Проверка `CNT >= 1` до чтения — правильно, хост мог прислать пустой пакет.

## 2.6. Клавиатура — `kbd_service()`

`USB.c:582`. Вот где реализовано «каждый символ = два отчёта»:

```c
if(usb_state != ST_CONFIGURED) return;
if(BDT[BD_EP1_IN].STAT & _UOWN) return;   // предыдущий отчёт ещё у SIE

for(uint8_t i = 0; i < EP1_SIZE; i++) ep1_in_buf[i] = 0;

if(kbd_release)
{
  kbd_release = 0;    // отчёт «всё отпущено» — буфер уже обнулён выше
  kbd_arm_report();
  return;
}

RingBuf_Available(&avail, &kbd_rb);
if(avail == 0) return;
if(RingBuf_DataRead(&key, 1, &kbd_rb) != RINGBUF_OK) return;

ep1_in_buf[0] = (uint8_t)(key >> 8);      // модификаторы
ep1_in_buf[2] = (uint8_t)(key & 0xFF);    // usage ID
kbd_release = 1;                          // следующий вызов пошлёт «отпустили»
kbd_arm_report();
```

Флаг `kbd_release` — вся машина состояний клавиши. Чередование «нажали /
отпустили» строго обязательно, иначе символ пойдёт автоповтором.

Проверка `_UOWN` в начале — это контроль потока. Хост опрашивает EP1 раз в 10 мс
(`bInterval`), а `kbd_service()` вызывается каждую 1 мс из SOF. Девять вызовов из
десяти просто упрутся в `_UOWN` и выйдут. Итоговая скорость печати — около
50 символов в секунду.

### Кольцевой буфер клавиш

`USB.c:263` — использование `ringbuf` с ячейкой в 2 байта:

```c
static RINGBUF_t kbd_rb;
static uint8_t   kbd_rb_mem[USB_KBD_BUFLEN * 2];   // 64 ячейки x 2 байта
...
RingBuf_Init(kbd_rb_mem, USB_KBD_BUFLEN, 2, &kbd_rb);
```

Одна ячейка = одно `uint16_t` вида `(модификаторы << 8) | usage`. Поэтому
`RingBuf_DataPut(&key, 1, &kbd_rb)` кладёт **одну ячейку**, то есть 2 байта.
Упаковка и распаковка симметричны.

### Синхронизация с основной программой

`USB.c:792`, `USB_kbd_putkey()` вызывается из `main()`, а `kbd_service()` — из
прерывания. Оба трогают `kbd_rb`, поэтому:

```c
ie = PIE2bits.USBIE;
PIE2bits.USBIE = 0;          // глушим только USB, не все прерывания
RingBuf_Available(&avail, &kbd_rb);
if(avail >= (USB_KBD_BUFLEN - 1)) { PIE2bits.USBIE = ie; return 0; }
RingBuf_DataPut(&key, 1, &kbd_rb);
PIE2bits.USBIE = ie;
```

Гасится только источник конфликта, а миллисекундный таймер и UART продолжают
работать. Сохранение и восстановление прежнего состояния `ie` вместо безусловной
единицы — тоже верно, вызов не ломает вложенность.

## 2.7. Как всё сходится в `main.c`

```c
sys_init();       // обязательно первым: PLL 48 МГц (без него USB невозможен)
                  // + таймер 1 мс, на котором держатся get_ms() и delay_ms()
...
USB_init();       // подключение к шине

while(1)
{
  if(USB_is_configured() != usb_was_ready) { ... }   // отслеживаем энумерацию

  if(dbio_getstring(strrx, 50, 5) > 0)
  {
    if(USB_is_configured())
    {
      USB_kbd_putstring(strrx, 50);   // строка -> очередь клавиш
      USB_kbd_putkey(0x28, 0);        // usage 0x28 = Enter
    }
  }
  delay_ms(500);
}
```

Итоговая картина: `main()` только **складывает** символы в очередь и мгновенно
возвращается. Всё остальное — разбор SETUP-запросов, энумерация, нарезка
дескрипторов, чередование нажатий и отпусканий — происходит в прерывании, по
событиям от хоста. Ровно та реактивная модель, о которой шла речь в самом начале.

Проверка `USB_is_configured()` (`USB.c:782`) учитывает и suspend:

```c
return (usb_state == ST_CONFIGURED) && !UCONbits.SUSPND;
```

То есть на спящем ПК устройство честно скажет «не готово», а не будет писать в
никуда.

## Что стоит знать про этот код

Стек накрывает все обязательные тонкости: отложенный `SET_ADDRESS`, ZLP, порядок
записи `UOWN` последним, чтение `USTAT` до сброса `TRNIF`, `PKTDIS`, таймаут на
ожидании SE0. Это не учебная заготовка, а рабочая реализация.

Сознательные ограничения, о которых полезно помнить, если проект будет расти:

- **Одна клавиша за раз.** В отчёте заполняется только `ep1_in_buf[2]`; аккордов
  из нескольких обычных клавиш не будет (модификаторы работают).
- **Только US-ASCII.** `ascii2usage` покрывает 0x00…0x7F, кириллица не пройдёт.
  И то, что появится на экране, зависит от раскладки в ОС, а не от устройства.
- **Нет remote wakeup.** В `bmAttributes` стоит `0x80`, разбудить спящий ПК
  устройство не сможет.
- **EP1 OUT объявлен, но не включён** — `BD_EP1_OUT` в BDT просто не используется.
- **VID/PID `04D8:003F`** — демонстрационная пара Microchip, годится только для
  макета. Для продукта нужны собственные, полученные в USB-IF.
